## 1. What was actually wrong (both problems)

### The install problem
The game has been installable for a long time — `manifest.json`, the `window.PWA`
helpers, `beforeinstallprompt` capture, all already there. The only thing advertising
it was a chip in the top-left corner that **auto-hid after 10 seconds**. So nearly
nobody installed and nearly everybody played in a browser tab.

### The cross-device problem
Progress **is** cloud-backed and always was — offline mode was removed
(`index.html`, `renderAuthGate`), every player has an email+password Supabase account,
and there is no guest path. **Players do not get a brand new account on another
browser.** What they got was a *half* account.

The reason is that `Profile` has three whitelists and one non-whitelist:

| Path | Behaviour |
|---|---|
| Local **save** | `JSON.stringify(Profile)` — the whole object. No whitelist. |
| Local **load** | explicit whitelist |
| Cloud **save** | explicit whitelist (`forgeSmall`) |
| Cloud **load** | explicit whitelist (hydration in `cloudFetchProfile`) |

A field added to `Profile` persists locally for free, is restored locally if someone
remembers the load whitelist, and **is never uploaded unless someone remembers both
cloud halves**. It then looks perfect on the device that made it and is missing
everywhere else. That has already happened to `itemInventory`, `archonDeck`,
`sideDeck`, `socketedGems`, `heroLoadouts`, `bagsOwned`/`bagCap`, and three reset
stamps — every one found only after players lost data.

Twelve more were still broken. The camp gap had a clear shape: **the camp's identity
travelled, its live state did not.**

## 2. The install gate — `public/src/install/gate.js`

A full-screen wall over the game in a browser; the way through is to install.

**It only walls browsers that can finish an install.** These classify as `none` and
play in the browser exactly as before — walling them is a blank screen they bounce
off, not a funnel:

- Firefox desktop (no PWA install of any kind)
- In-app browsers — Discord, Instagram, Facebook, X, TikTok. **This is a lot of
  shared-link traffic.**
- Chrome/Firefox/Edge on iOS (only real Safari can Add to Home Screen)
- Incognito (`beforeinstallprompt` never fires)
- Desktop Safari (Add to Dock is a File-menu item with no API)

Three walls: one-click install (Chromium), Add to Home Screen instructions (iOS
Safari), and a **handoff wall** shown after install or on a later visit from a device
that already has the app. The handoff wall is the one that kills two-sessions-on-one-
account — it refuses to be a second playable surface.

**It is never a trap.** "Continue in the browser instead" appears the moment a player
declines the native dialog, and on a timer regardless. Two constants at the top of the
file:

```js
const ESCAPE_AFTER_MS   = 45000;  // time on the wall before the escape link appears
const ESCAPE_ON_DECLINE = true;   // also reveal it when they dismiss the dialog
const PROMPT_WAIT_MS    = 4000;   // no install event by now -> stand down entirely
```

`ESCAPE_AFTER_MS = 45000` is a judgment call, not a measured number. Raise it to
tighten the funnel; lower it to lose fewer impatient players. Setting it to `Infinity`
gives a hard wall **at the cost of every player whose install silently fails for a
reason we did not predict** — do not do this to the iOS wall, which has no other exit.

Support escapes: `__mg.gateOff()` clears the wall for a tab, `__mg.gateTier()` reports
the classification. `__mg.installChipOff()` hides the toolbar chip.

**Also changed:** the install chip no longer auto-hides after 10s. That was right when
every player saw it; now the only people who reach it have already dismissed the gate
or cannot install, and for them the chip is the one route back.

### Verified
8 user-agent profiles routed correctly in Chromium, plus accept, decline, escape,
stand-down, already-installed, escaped-session, standalone launch, iOS
`navigator.standalone`, and tab-converts-to-app. Two real bugs were found and fixed
during that: a `requestAnimationFrame` fade that left an **invisible wall over a
scroll-locked page** in a background tab, and `display:flex` on the iOS `<li>`s that
shredded the instructions into scattered blocks.

### NOT verified
**Never run on a real iOS device.** The iOS wall and the Add to Home Screen flow were
only exercised via user-agent emulation. Test on a real iPhone before leaning on it.

## 3. The 12 fields that now travel

All were localStorage-only. Added to **both** halves — `forgeSmall` in
`cloudSyncProfile`, and the hydration block in `cloudFetchProfile`.

`bunkhouse`, `research`, `memorial`, `campDefense`, `campMissing`, `campRival`,
`campLastTick`, `campRaidLastTick`, `campPoweredUntil`, `campRepairUntil`,
`campConsumeFrac`, `campTrickleFrac`

### The merge rules are deliberately not uniform

Blind overwrite would have created new bugs. Each field got the rule it needs:

| Field(s) | Rule | Why |
|---|---|---|
| `campLastTick`, `campRaidLastTick` | MAX | An **earlier** tick is not a harmless stale read — it re-charges upkeep for a window already paid and re-fires a raid that already happened |
| `campPoweredUntil`, `campRepairUntil` | MAX | Keeps the longer of two **paid** windows |
| `campDefense` | MAX | Fortify level is bought; no stale row may lower it |
| `memorial` | union by `ts\|name` | Append-only — a death on either device is real |
| `campMissing` | **no union**, seed empty only | MIA entries are **removed on rescue**; a union would resurrect survivors who came home |
| `campRival`, both carry fractions | local wins if present | Live state belongs to the device actually playing |
| `research` | MAX per project, keep local `active` | Never un-completes; a second device cannot cancel a running project |
| `bunkhouse` | `built` only goes up, clocks MAX | Paid structure; MAX `lastCollect` stops one billet payout being claimed twice by device-hopping |

`campMissing` is the one to remember — it is the only array here that **shrinks**.

`bagTier` was flagged by the audit and is **not** a bug: `_recalcBagCap()` derives it
from `_bagsOwned()`, which does sync. It is documented in `KNOWN_DEVICE_LOCAL`.

## 4. The two new checks — run both before every deploy

```bash
node _syncaudit.mjs    # is every field on BOTH halves of the sync?
node _mergetest.mjs    # is the merge logic actually correct?
node _synckcheck.mjs   # existing — index.html syntax  (NOT build.mjs)
```

`_syncaudit.mjs` finds the upload payload and the local restore block **by content,
not line number**, so it does not rot when something is inserted above them. It
reports fields uploaded but never hydrated, and fields restored from localStorage but
never uploaded. Exit 1 on regression. Currently: 112 forge keys uploaded, 112
hydrated, zero gaps.

`_mergetest.mjs` **extracts the real hydration block out of `index.html`** and runs it
rather than re-implementing it — so it tests the shipped code, not a copy. 34 cases.
If someone edits the merge, this tests the edit.

Both are report-only and touch no game code.

## 5. 🔴 Read this before deploying

### The gate and the sync fix are in the SAME build
Earlier in the session I said to ship the sync fix first and turn the gate on after.
**That is not possible as things stand** — both are on this branch under one version
bump, so deploying ships them together. Plan around that.

### Why it matters
On iOS a home-screen PWA gets **its own storage container, separate from Safari**.
Installing therefore means empty `localStorage` and a **full cloud restore** — exactly
the path these gaps live on.

So there is a window: deploy → a player's very first post-deploy action is installing
on iOS → their cloud row does not have the camp keys yet (their normal browser has not
re-uploaded since the deploy) → the camp opens with its live state reset.

### Why the window is bounded and self-healing
The data is **not destroyed** — it is still in Safari's `localStorage`. And the merge
rules recover it: when that player next opens the game in Safari, local load restores
the camp, `MAX` beats the zeros the PWA wrote, `campMissing`/`campRival` take the
local copy, `memorial` unions, and `bunkhouse.built` goes back to 1. It re-uploads
correctly. Nothing needs manual repair.

A player only has to open the game once on their normal browser after the deploy to be
fully protected.

### Options, pick one
1. **Ship as-is** and accept the bounded window above. Simplest, and the damage
   self-heals.
2. **Put the gate behind a flag** so you can deploy the sync fix now and turn the wall
   on in a few days once players' cloud rows carry the camp keys. Not built — ask.

### Existing players are not fixed retroactively
Anyone who **already** lost camp state on a second device cannot get it back. It was
never uploaded. This fix stops the bleeding; it does not restore history.

## 7. Settled — please don't re-derive these

- **No native game client, and no app stores.** Apple takes 30% on digital goods
  (your Aza packs run ~2.9% + 30¢ through Stripe today) and Google Play Billing
  applies the same way to a Bubblewrap/TWA wrapper — wrapping the PWA does not route
  around it. Cash-out to real money also invites a different review entirely. The PWA
  install **is** the client.
- **The PWA was never the missing piece.** Updates, maintenance messaging, redeem
  codes and cash-outs are all server-side or already built; none of them needed a
  client.
- The existing `CLAUDE.md` bans stand: no Discord webhooks, no image/video upload.

## 9. Gotchas that cost real time this session

- **`_synckcheck.mjs` needs `npm install` first** — `terser` is a devDependency and
  was not present. `build.mjs` is still not the syntax checker.
- **`pkill -f "http.server"` killed its own shell** and silently ate the rest of a
  compound command (exit 144). Check what a `pkill` pattern matches.
- **`requestAnimationFrame` never fires in a background tab.** A RAF-gated fade-in on
  an overlay that also scroll-locks the page = an invisible wall over a frozen game.
  Use `setTimeout` for anything that must appear regardless.
- **The first sync audit produced 12 false positives.** Hydration happens in two
  blocks with different variable names (`f.__key__` and `data.forge.__key__`), and the
  first regex only knew one. Always check a "bug list" against the real code before
  reporting it.
