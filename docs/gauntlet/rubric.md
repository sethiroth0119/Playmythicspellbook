# THE BAR — rubric derived from this repo's own best files

  - Comments name the specific failure, with evidence
      excellent: Where a rule exists because something broke, the comment names the incident and its measurable consequence, in the code that prevents it: "95 metal and 70 supplies deducted, 'refunded', and gone"; "270 units destroyed, clipped:false, and the 36h timer reset. Measured, not theorised"; "charged the player 50,000 Cinder for a building that never persisted"; "+602,357 🔥 of reconcile gains in one week"; "client 661,147 vs server 1,143"; five real account fingerprints pasted into a migration header. Recurrences are counted ("THE FIFTH SILENT-SAVE BUG THIS PROJECT HAS SHIPPED", "deleted paid-for buildings four rounds running") so a reader knows the failure is a class, not an instance. Where a claim is not measured, it says so.
      failure:   Comments that restate the code ("// increment runs_used"), or warn in the abstract ("be careful with refunds", "this is important for security") without naming what went wrong, who lost what, or how it was detected. A defensive branch with no explanation of the input that made it necessary. A number in a comment with no provenance. Confident assertions about behaviour nobody measured, presented as fact.
  - Rejected designs are recorded, with the reason they lost
      excellent: The alternative that was considered and turned down is written into the file, named, and costed: "🔴 THIS IS DELIBERATELY NOT MERGED INTO CAMP_FACILITIES, and that is the whole design decision", followed by the concrete cost of the merge (every read site grows a branch). "deliberately NOT a second wallet sitting beside corp_treasury." Deriving prereqs mechanically from `inputs` is rejected because "THE INPUT GRAPH HAS A CYCLE AND THIS TREE MUST NOT." Taking the max of admin override and paid tier is rejected because it would make demotion impossible. Deliberate NON-enforcement is also recorded with its business reason (the member cap is not duplicated server-side because it "would silently void a purchase"). Settled calls are marked as settled so they are not relitigated.
      failure:   Code that reads as if only one option was ever on the table. Silent removal or quiet inversion of an existing decision. Re-deriving something the repo has already ruled out, or arguing the other side of a settled call in a comment. Deleting an inherited WHY comment while changing the code it guards, so the reason is lost with the line.
  - Declared authority when two systems could disagree
      excellent: Wherever the same fact lives in two places, one is named the authority and the consequence of drift is spelled out: "GARAGE_RIGS in worker.js is the pricing authority and is what Stripe actually charges. If these two disagree the player is shown one price and billed another"; "THE EFFECTS TABLE IS THE SINGLE SOURCE OF TRUTH… the shop can never advertise a number the engine does not deliver" (and the shop copy is generated from it, not copied); "THE CAP REPORTED HERE IS THE LEDGER'S OWN CAP, NOT A LOCAL BELIEF"; "RESOURCES DO NOT LIVE ON Profile.resources — the task doc asserts it and that is WRONG." Shared contracts are PASSED rather than redeclared ("so production cannot become a third idle policy"). Where duplication is genuinely unavoidable it is bounded, cross-referenced, and paired with a test on each side.
      failure:   The same tuning number, cap, label, or rule copied into a second file with nothing saying which one wins. A cached total maintained beside the history it is derived from. Two generators, two rarity ladders, or two ownership flags that can disagree, with no reconciliation and no note. A client value trusted as authority for something another player pays for. Silently believing a spec document over the code it describes.
  - A feature failure cannot take the game down
      excellent: Absence is a designed state, not an error path. "An absent module must never change a payout" — a missing module yields exactly the pre-feature behaviour, and the identity is stated as what "makes it safe to ship." Every seam method is try-wrapped and returns a typed default; nothing throws at import time; the bridge is missing → the module registers, stays inert, and warns once. Supabase calls return `{ok:false, missing, error, rows: []}` rather than throwing, and "missing table" is distinguished from "empty" so the UI can say "run the SQL" instead of "something went wrong." A neutral object of the same shape is returned from both the no-data path and the catch, so callers never branch on failure. Data assertions are exported, not run at import, "because a data assertion that throws on load would take the whole city down over a tuning typo."
      failure:   A module that reads a bare lexical global (`Profile`, `Corp`, `Forge`, `RESOURCES`, `root`) or assumes `window.Foo` exists; a top-level statement that can throw during page load; an unguarded `.from(`/`.rpc(`; a thrown error crossing a seam. Treating a missing table as an empty market. A degraded path that silently succeeds where it should refuse (a no-op `save`/`addGems` on a null bridge). Renaming or removing a catalog id that a save-pruning routine will then silently delete rows for.
  - Security commentary reads like a review, and states its own limits
      excellent: A 🔒 block that argues line by line: what the pinned `search_path` prevents, why the authority is re-read inside the function instead of taken from an argument ("Read it fresh; never trust input"), why there is NO parameter naming a user, what the revoke/grant pair closes. RLS is treated as the entire boundary: recursion is routed through SECURITY DEFINER helpers scoped to the caller's own question, `using (true)` appears only on something genuinely public and says so, and a policy that cannot express its intent is DELETED rather than commented — "POSTGRES RLS HAS NO COLUMN GRANULARITY… The comment described an intent the mechanism could not express" — with the grant revoked as well "so the denial does not depend on this policy staying deleted." The honest boundary is published: what the server cannot check, and "Do not read this file as claiming otherwise." Where the fix must be server-side, it says why a client fix cannot work.
      failure:   A policy comment that describes what the policy does instead of who it stops. A row-level UPDATE policy with a comment promising the owner may change only certain columns. `security definer` without `set search_path`, or without `revoke all … from public, anon` naming the exact argument types. A function that trusts an id, an amount, a price, or a user handed to it by the client. A self-referential policy on the table it protects. An unconstrained signed `amount` on an append-only table. Overstating the guarantee — claiming a bound is a recomputation.
  - Money and ledgers: atomic, append-only, and reported rather than swallowed
      excellent: Verify every leg before deducting any; deduct in an order justified by which leg can fail for outside reasons; record what was taken and unwind in reverse; hand the refund closure back so a later record-failure can also unwind. Refunds use the uncapped undo path, payouts use the capped add path, and the distinction is explained as a safety property. Balances are `sum(amount)` with no stored total; append-only is enforced by revoked grants, not asserted by a comment; sign and kind are constrained. Every mutator across a seam returns a boolean and a `false` is converted into a throw at one chokepoint so the refund branch stays live. Spends check the return value, are confirmed first, and unwind on a failed write with a toast that names the real error. What the ledger actually took is measured, never assumed from the request.
      failure:   Raw `Profile.gems` arithmetic, or a spend whose boolean return is ignored. A cost read directly out of the catalog, bypassing the one function that applies the pricing dial, so the UI and the spend disagree. A refund through the capped add path. `try { … } catch (e) {}` around a persist call, making a refund branch dead code while the caller still returns `{ok:true}`. A stored balance/earnings/reliability column that is UPDATEd. A client-computed payout, a caller-supplied amount, or a counter the client can write. A missing level treated as free rather than unaffordable.
  - The seam is explicit, one-way, and complete on both sides
      excellent: The globals trap is named as a language mechanic, not a style preference — lexical `const` bindings are not `window` properties — and everything the module needs is handed over at one construction site. Accessors are functions, never snapshots, with the staleness reason stated. Both halves land in the same change: the real bridge and its full-shape NULL_BRIDGE, or the upload key and the hydration read, with a merge policy stated per field and a distinct reason for each half (paid things union; anti-farm counters take the max). Resolution duck-types a known method rather than testing truthiness, so a half-built object is rejected. Dead hooks are labelled honestly with what was grepped for and how to wire it later. The standing instruction is written down: add it to the bridge, do not reach around.
      failure:   A module reaching for a bare global, or a new top-level system added to the legacy file instead of the feature directory. A capability added to one side of a seam only. A captured snapshot handed across instead of an accessor. `window.Foo || FALLBACK` accepting a partially constructed object. Debug/console seams (`window.__mg`) pressed into service as the feature bridge. A profile key that saves but is absent from the restore whitelist or the hydration block. An overlay whose listeners are attached directly to elements a repaint replaces.
  - The artifact checks itself, and dates its own claims
      excellent: A migration ends with a counted verify whose expected numbers were actually run, including at least one NEGATIVE assertion proving a dangerous policy is absent — plus the memory of why: "⚠ COUNT THEM. r9 asserted policies = 6 when the file created 5, and the mismatch survived into two documents because the query was never run." Data rules are expressed as a runnable audit rather than prose acceptance criteria. Provisional decisions are marked with their expiry ("this comment exists to be deleted by whoever adds one"). Lists that can go stale carry a warning explaining how staleness would invert the check. A file states its own status honestly ("THIS FILE HAS NEVER BEEN RUN") and what applying it does and does not achieve. DDL is idempotent and re-runnable throughout.
      failure:   A migration ending on DDL, or a verify with invented expected counts, or one that only proves the good policies exist and never that the dangerous one is absent. `create table` / `create policy` without `if not exists` / `drop policy if exists`. Acceptance criteria restated as prose no one can run. A hardcoded parallel list with no note that it must track another. Claiming a migration has been applied, or citing a false-green from a checker that does not actually inspect the file type it was handed. Stale line numbers or line-number references cited as current.
  - Failure is visible and actionable to the player
      excellent: Every stop has a distinct code and returns both a `reason` the UI is required to print and a `fix` naming the concrete thing to go do, with the resource named exactly ("'missing inputs' on a building with three of them tells the player nothing actionable"). Warning chrome is deliberately loud, and the CSS says why: "A stopped building that looks the same as a running one is the single most common 'the game is broken' report." A cost that names an unknown resource id SHOWS, flagged, rather than vanishing while still blocking the build. Empty states are instructions. Error messages name the real error rather than guessing at a cause; each documented error code gets its own message and an unknown code says so out loud. Degradation modes are legible ("the module 404'd" is said, not silently absorbed).
      failure:   A silent no-op refusal; a disabled button with no stated reason; a blank panel where a "not set up yet" line belongs. A generic "something went wrong" that hides a specific, known condition. A toast that blames a cause it has not verified — telling an admin to run SQL they already ran. Player-supplied text interpolated into HTML without escaping. Diagnostics that require reading the console.
  - Legacy edits are additive, minimal, and complete
      excellent: A change to a 223k-line file is a small additive hunk that follows the local idiom, extends the neighbouring entry's comment style, and preserves every existing comment. New parameters are optional so existing callers are untouched, and the reason for the addition is written at the call site. Every site that must move for the change to be correct is found and moved together — including the duplicated ones the spec forgot — or the drift is documented. Unrelated defects noticed in passing are noted, not bundled into the change. Deploy/cache-invalidation knobs that must move together do move together.
      failure:   Reindentation, restructuring, or comment deletion in the legacy file. Copying the wrong neighbouring pattern (a raw balance mutation, a `length`-based slot assignment) because it was nearest. Editing one of several duplicated sites and assuming the rest read it. A ratified public function silently wrapped, reassigned, or given a new early return. Unrelated legacy fixes smuggled into a feature branch that touches paid or economy rails. A new key or module shipped without its cache-bust and version bumps.
